# AI 出行规划评测体系

## 1. 评测目标

产品目标是把用户的自然语言需求转成可执行、可解释、可持续修改的本地出行方案。因此不能只判断“接口有没有返回”，而要回答四个问题：

1. 是否正确理解用户？
2. 是否使用了正确的真实世界上下文（城市、起点、时间）？
3. 是否生成了满足约束、实际可执行的路线？
4. 出错时能否定位到意图、追问、召回、路线或总结中的具体步骤？

## 2. 质量维度与条例

| 维度 | 核心条例 | 典型失败 |
| --- | --- | --- |
| 意图理解 | 明确表达的人数、城市、时间、预算、偏好和避雷条件不得丢失；用户新表达优先于历史状态 | 城市识别错、人数回默认值、偏好丢失 |
| 起点定位 | 用户明确起点 > 浏览器 GPS > 城市级兜底；不得把兜底地点冒充当前位置；更换起点必须清除旧坐标 | “从国贸出发”仍使用 GPS |
| 追问决策 | P0 信息缺失才阻断；已知城市或 GPS 时不得重复问城市；一轮最多追问一次；P1 信息可采用合理默认值 | 已传城市仍追问、反复追问 |
| POI 与路线 | 有效规划 Query 应产生至少一条路线；凑不够三条时返回已有路线；站点、时间、成本必须有效；硬约束优先于偏好 | 召回很多 POI 但路线为 0 |
| 多轮状态 | 修改只改变用户明确修改的字段；起点、城市和未修改硬约束应继承；新规划不得污染旧规划 | 第二轮丢起点、修改预算导致城市变化 |
| 稳定与观测 | 单条异常不得中断批次；所有关键步骤有 Trace；失败需归因到具体步骤；不得暴露密钥或内部异常给用户 | `NoneType`、ConnectError、problem_step 为空 |

硬性通过标准：

- 任一系统异常、错误城市、错误起点来源、无路线且无有效追问，整条用例失败。
- 明确硬约束缺失，整条用例失败。
- 只有展示措辞差异且不影响执行时，才允许作为非阻断质量项。

## 3. 用例分层

- P0 冒烟：服务可用、返回结构完整、无异常。
- P0 主链路：典型 citywalk、餐厅聚餐、附近放松、指定起点、GPS 起点。
- P1 边界：信息不足、偏好冲突、路线不足三条、无匹配 POI、跨城市定位。
- P1 多轮：追加偏好、修改预算、更换起点、局部换站、整条重规划。
- P2 鲁棒性：口语、省略、错别字、混合中英文、长输入、重复输入。

每次改动至少运行 P0；合并前运行全部固定集。线上发现的问题应先沉淀成回归用例，再修复。

## 4. 指标与判读

- 用例通过率：所有硬断言均通过的比例。
- 综合得分：各用例分维度检查的平均分，用于观察改善趋势；不能替代 P0 通过率。
- 分维度得分：意图理解、起点定位、追问决策、路线可执行性、过程可观测性、系统稳定性。
- 问题聚类：按失败代码统计次数和受影响用例，优先处理高频且位于主链路上游的问题。
- 延迟：记录单条与整批耗时；功能正确前不以延迟优化掩盖质量问题。

优先级计算原则：影响用例数 × 严重性 × 链路上游程度。通常顺序为：系统异常 > 起点/城市/硬约束错误 > 无路线 > 多轮状态错误 > 偏好质量 > 文案体验。

## 5. 使用方法

启动前后端后，从首页右上角进入“测评”。

- 输入框留空：运行 20 条分层基线用例，覆盖意图、定位、追问、路线、偏好、多轮与鲁棒性。
- 每行输入一条消息：运行自定义探索批次，最多 20 条。自定义 Query 没有人工期望时主要用于发现异常、空结果与流程问题，不代表完整准确率。
- 页面先看“重点问题”和分维度得分，再展开失败用例查看输入、输出、失败断言与 Trace。

接口：`POST /api/evaluation/run`。

自动化回归：

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest app\tests
```

## 6. 优化闭环

1. 固定当前代码和用例集，运行并保存基线。
2. 按问题聚类选一个最高优先级问题。
3. 将失败 Query 固化为带期望的回归用例。
4. 修复最上游根因，不为单条 Query 写特殊返回。
5. 重跑受影响分层与全量 P0，比较通过率、维度得分和新增回归。
6. 只有在旧问题消失且没有主链路退化时合并。
