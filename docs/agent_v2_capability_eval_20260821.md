# Agent V2 能力基线评测报告

> 本文保留修改前的 13/30 基线和原始问题诊断。当前 Harness V3 已提升到 24/30；对比结果与实现说明见 [Harness V3 版本说明](./agent_harness_v3_version_notes_20260821.md)。

评测日期：2026-08-21  
运行时：`v2`  
模型：`openai/gpt-5.6-sol`  
数据集：`agent-v2-capability-v1`  
策略：`lynn-agent-v2`

## 结论

当前 Agent V2 的架构主链路已经成立，但产品效果还没有达到可以放心默认上线的程度。

- 30 个 Case 中严格通过 13 个，通过率 43.3%，平均评分 79.2。
- 12 个进入 `complete` 的请求全部返回了 3 条路线，其中 11 个严格通过。说明“一旦成功进入完整规划，结果质量总体稳定”。
- 当前主要瓶颈不在基础字段理解，而在“是否该追问”的决策、起点类型兼容、无解恢复和最终路线筛选。
- 本轮只运行 1 次，不能把结果称为 `stable-pass@3`；稳定性需要修复 P0 后再重复三轮验证。

## 覆盖范围

本批数据共 30 条，分为 6 组，每组 5 条：

1. 结构化理解：城市、人数、预算、时长、偏好和缺失字段追问。
2. 城市与起点定位：用户明确地点、GPS、定位城市冲突和地点覆盖。
3. 时间与隐式需求：午餐、晚餐、已吃饭否定、非饭点和跨饭点行程。
4. 多轮状态：追加偏好、修改预算、更换起点、补充城市和路线问答。
5. 规划与偏好：雨天室内、夜景、低预算、亲子、少走路和部分路线返回。
6. 鲁棒性：口语、中英混合、长输入、附近夜间需求和无本地数据城市。

## 已经表现较好的能力

- 人数、城市、饭点和“已经吃过饭”等明确语义的结构化理解整体正确。
- 用户没有明确起点时可以使用 GPS；用户明确地点能够覆盖 GPS 的优先级规则在非异常 Case 中成立。
- 多轮追加“少走路”、后续更换起点、追问后补充城市和路线问答均通过。
- 进入完整规划后能够稳定产出 3 条路线，并保留 LYNN 多目标方案。
- `infeasible`、澄清、工具调用和诊断过程均能进入结构化 Trace，定位问题比 V1 清楚。

## 真实问题与根因

### P0：非阻断歧义被当成阻断问题

6 个 Case 出现不必要追问，例如要求用户解释“半日游”究竟多长、“一天”是否指 24 小时、已有 GPS 时仍追问具体起点。

根因是 Policy 当前把理解结果里的所有 `ambiguities` 都当成阻断字段。应改为：只有缺少城市且无定位、用户明确硬约束互相冲突、必须取得授权才能放宽的字段才阻断；半日游、一天游、附近、Citywalk 等应使用产品默认值并在结果中说明。

### P0：地点字符串未兼容 `LocationRef`

3 个 Case 抛出未捕获的 Pydantic `ValidationError`。模型有时把“国贸”“春熙路”直接输出为字符串，而 Reducer 只接受 `LocationRef` 或字典。

修复方式是在 Reducer 边界统一将字符串转为 `LocationRef(name=..., precision="named")`，并添加单轮、多轮和无本地数据城市的回归测试。

### P0：规划无解恢复仍不足

13 个 Case 没达到期望路线数，8 个进入 `infeasible`。主要现象包括：

- 14:00–18:00 只与晚餐窗口轻微重叠，也被强制要求正餐，导致短行程无解。
- “一天”可能被解释为 24 小时而非约 8 小时的一日游。
- fallback 把“别走太多路”误写进商圈字段，导致 POI 检索提前失败。
- 部分请求已经产生多条 enriched/scored route，但最终 `selected_route_count=0`，说明最终筛选和前置约束口径仍不一致。
- 夜间、雨天、低预算场景中，`closed_at_arrival` 和 `duration_exceeded` 是主要拒绝原因，但恢复动作没有针对原因充分调整。

### P1：偏好 taxonomy 与评分口径不一致

5 个 `missing_preference` 中包含“夜景”与“看夜景”、“少走路”与“轻松不累”这类同义表达。这里既有 Agent 规范化不足，也有评分器只做字面匹配的问题。

建议把偏好统一到 canonical taxonomy，再让 Agent 状态、路线目标和评测断言都比较 canonical id，而不是比较中文展示文本。

## 评分器质量说明

本轮原始报告中有 7 个 `no_planning_outcome`，但这些响应实际明确返回了 `planning_outcome="infeasible"`。这是评分器误判，不是 Agent 没有结果。评分器已修正为接受 `complete / partial / infeasible / degraded` 等终态，并补充回归测试。

该误判与“路线不足”同时出现，因此修正后严格通过数仍是 13 / 30，但后续问题统计和维度评分会更准确。

## 推荐优化顺序

1. 兼容字符串起点，先把未捕获异常降为 0。
2. 将歧义分为 blocking / non-blocking，并为半日游、一天游、附近和 GPS 建立确定性默认规则。
3. 收紧饭点隐式需求：只有行程覆盖足够长的用餐窗口或用户明确提出时才设为必需角色。
4. 统一候选生成、路线验证和最终选择的时长、营业时间、预算口径；针对拒绝直方图执行恢复。
5. 建立偏好 canonical taxonomy，修正 Agent 和评测器的同义表达处理。
6. 修复后先跑 30 条单轮回归，再对 P0 主链路执行 3 次重复评测，记录真正的 `stable-pass@3`。

## 数据可信度边界

- 本报告来自一次真实模型与真实 Agent V2 批量执行，不是静态模拟。
- 30 条 Case 对方向性诊断足够，但不足以代表所有城市、地图数据质量和长尾表达。
- 单轮结果不能证明模型稳定性；只有三轮重复结果才能用于稳定性门禁。
- 完整 JSON 保存了每条输入、输出、状态 Patch、工具调用和失败诊断，可逐条复核。
