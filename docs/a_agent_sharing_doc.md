# A 侧 Agent 编排分享文档

## 这部分要解决什么问题

我们现在做的是一个出行规划 Agent。用户不是一次性把所有信息填进表单，而是像聊天一样不断补充、修改、追问：

```text
上海两人一日游，喜欢拍照
我还要吃饭
少排队一点
第二个点换个餐厅
两个地点之间怎么过去
```

如果系统只是“每句话都重新丢给大模型生成路线”，很容易出现几个问题：

- 忘记上一轮上下文，比如用户补充“我还要吃饭”后，系统忘了原来是上海、两人、一日游、喜欢拍照。
- 过度重规划，比如用户只是问“两个点之间怎么过去”，系统却重新生成了一整条路线。
- 大模型编造事实，比如没有路线工具结果，却说出了看似具体的交通时间、距离、餐厅和价格。
- 前后端联调困难，因为每一轮为什么这么判断、哪里失败了都看不清。

A 侧要解决的核心问题，就是把这个系统从“聊天触发路线生成”升级成一个有状态、可解释、可调试、可回归测试的出行规划 Agent。

## A 侧在整个项目中的位置

项目整体链路可以理解为：

```text
React 前端
  -> FastAPI /api/chat
  -> A 侧 Agent 编排
  -> B 侧 POI / 路线 / 重规划工具
  -> 高德或 mock 地图路段
  -> C 侧路线卡片和 Agent trace 展示
```

A 侧是中间的“调度和解释层”。它不直接负责路线算法，也不负责前端 UI，而是负责把用户的话变成稳定的结构化请求，再调用正确的工具，最后把工具结果解释给用户。

简单说：

- A 负责听懂用户想干什么。
- A 负责记住当前这趟行程的状态。
- A 负责判断要不要澄清、重规划、局部替换或只回答问题。
- A 负责把自然语言转成 B 侧工具能执行的结构化输入。
- A 负责把 B 侧工具结果整理成用户能看懂的回复。
- A 负责把每一步过程写进 trace，方便 C 展示和团队调试。

## 一句话方案

LLM 负责理解复杂语言和润色表达；显式状态负责记住上下文；少量规则负责稳定决策；路线工具负责真实规划；trace 和测试负责发现问题。

也就是：

```text
LLM 理解
  + TripState 记忆
  + Policy 决策
  + Tools 执行
  + Trace 解释
= 稳定可调试的出行规划 Agent
```

## 为什么不能让 LLM 直接自由规划

大模型很适合理解用户自然语言，比如识别“我还要吃饭”是在追加需求，“换成杭州吧”是在修改城市，“第二个点换个餐厅”是在局部替换。

但它不适合作为唯一决策者。原因是路线规划里有很多必须稳定的业务规则：

- 用户没提到的城市、人数、预算、时长应该继承上一轮，不能被默认值覆盖。
- 问路线细节时不能重新规划。
- 局部替换时不能把整条路线推倒重来。
- 没有路线工具结果时不能编造距离、时间、价格和 POI。
- 工具失败时必须让系统知道失败原因，而不是生成一段看起来正常的文案。

所以我们的设计是：LLM 只输出结构化理解，真正的状态合并、流程选择和工具调用由后端显式规则控制。

## A 侧核心链路

A 侧每次收到用户消息后，理想流程是：

```text
1. MessageRouter / QueryUnderstanding
   判断用户这句话属于哪类意图

2. IntentDelta
   抽取本轮新增、修改、删除了什么

3. TripState
   和上一轮状态合并，得到当前完整旅行状态

4. ClarificationPolicy
   判断是否缺关键字段，是否需要追问

5. Policy / Planner
   决定本轮是新规划、全量重规划、局部重规划、路线追问还是普通聊天

6. Tools
   调用 POI、Route、Replan、Amap 等真实工具

7. Response Composer
   基于结构化事实生成用户回复

8. Agent Trace
   记录每一步判断、状态变化、工具结果和失败原因
```

这条链路的重点是“先理解，再合并状态，再决策，再调用工具”，而不是“用户说一句，大模型直接生成一段答案”。

## 三个最重要的结构

### 1. QueryUnderstanding：用户这句话是什么意思

`QueryUnderstanding` 只描述本轮用户话语的含义，不直接修改状态，也不直接调工具。

例如用户说：

```text
我还要吃饭
```

在已有上海一日游上下文时，应该理解为：

```json
{
  "turn_type": "add_constraint",
  "inherit_previous": true,
  "preserve_scenario": true,
  "reason": "用户在上一轮路线基础上追加吃饭需求"
}
```

几个典型判断：

| 用户表达 | 应识别为 | 含义 |
| --- | --- | --- |
| 上海两人一日游 | `new_plan` | 新建行程 |
| 我还要吃饭 | `add_constraint` | 在原行程上追加需求 |
| 换成杭州吧 | `modify_constraint` | 修改城市 |
| 少排队一点 | `add_constraint` 或全量重规划 | 改变整体偏好 |
| 第二个点换个餐厅 | `replace_stop` | 局部替换 |
| 两个地点之间怎么过去 | `route_detail` | 只回答路线细节 |

### 2. IntentDelta：本轮改了什么

`IntentDelta` 不保存完整行程，只保存这一轮对状态的变化。

例如用户说“我还要吃饭”，delta 可以是：

```json
{
  "added_preferences": ["吃好"],
  "added_must_include": ["meal_stop"],
  "target_route_ref": "current"
}
```

这样做的好处是清楚地区分：

- 上一轮保留下来的是什么。
- 本轮新增了什么。
- 本轮修改了什么。
- 本轮删除了什么。

这对多轮对话很关键。比如用户只是追加吃饭，不应该把原来的“拍照”偏好覆盖掉。

### 3. TripState：当前完整旅行状态

`TripState` 是当前会话里真正的旅行状态。

它记录：

- 城市
- 人数
- 出发时间
- 游玩时长
- 预算
- 场景
- 软偏好
- 隐含需求
- 必须包含的节点
- 当前选中的路线
- 锁定的站点
- 用户反馈历史

示例：

```json
{
  "city": "上海",
  "people_count": 2,
  "duration_hours": 8,
  "budget_per_person": 300,
  "scenario": "friends_citywalk",
  "soft_preferences": ["拍照", "吃好"],
  "implicit_needs": ["rest_stop"],
  "must_include": ["meal_stop"],
  "active_route_id": "route_balanced_1",
  "locked_stop_ids": []
}
```

这里最重要的是：用户没有提到的字段必须继承，不允许被 LLM 默认值覆盖。

## 约束分层

出行需求不能都混在一个 `preferences` 里，需要分层：

| 类型 | 示例 | 作用 |
| --- | --- | --- |
| 硬约束 | 城市、人数、时长、预算、出发时间 | 影响能不能生成路线 |
| 软偏好 | 拍照、少排队、少走路、吃好 | 影响排序和路线风格 |
| 隐含需求 | 一日游默认饭点、休息点 | 系统基于常识建议加入 |
| 必须包含 | 用户明确说要吃饭后的 `meal_stop` | 至少一条主推路线必须满足 |

举例：

```text
上海两人一日游，喜欢拍照
```

可以得到：

```json
{
  "hard_constraints": {
    "city": "上海",
    "people_count": 2,
    "duration_hours": 8
  },
  "soft_preferences": ["拍照"],
  "implicit_needs": ["meal_stop", "rest_stop"],
  "must_include": []
}
```

用户继续说：

```text
我还要吃饭
```

这时 `meal_stop` 应该从“隐含建议”升级为“必须包含”：

```json
{
  "soft_preferences": ["拍照", "吃好"],
  "implicit_needs": ["rest_stop"],
  "must_include": ["meal_stop"]
}
```

## 本轮到底应该做什么

A 侧需要根据 `turn_type` 决定本轮动作。

| turn_type | 系统行为 |
| --- | --- |
| `new_plan` | 初始化行程，生成新路线 |
| `add_constraint` | 继承原状态，追加偏好或必须节点，重新规划 |
| `modify_constraint` | 只修改明确字段，其他字段继承，重新规划 |
| `remove_constraint` | 删除指定需求，重新规划 |
| `route_detail` | 不重新规划，只回答当前路线细节 |
| `replace_stop` | 只替换目标站点，保留其他站点 |
| `remove_stop` | 删除目标站点并局部重排 |
| `lock_stop` | 锁定站点，后续重规划保留 |
| `compare_routes` | 不重新规划，只解释路线差异 |
| `general_chat` | 不进入路线规划 |

最容易错的是这三类：

- “少排队一点”通常是整体偏好变化，应继承硬约束后全量重规划。
- “这家餐厅排队 90 分钟”是当前路线里的动态事件，应局部重规划。
- “第二站怎么去”是路线细节追问，不应重新规划。

## 澄清策略

A 侧不应该像问卷一样连续追问。原则是：只有无法生成可执行路线时才问。

必须问的情况：

- 城市或区域缺失，且上下文里也没有。
- 用户目标太泛，比如“帮我安排一下”。
- 意图不清，比如不知道用户是想整条路线更省钱，还是只想换掉某一家店。
- 局部重规划无法定位目标，比如当前有多个餐厅，用户只说“换一家”。

不应该阻塞规划的情况：

- 没说人数，默认 1 人。
- 没说预算，默认中等预算。
- 没说出发时间，默认 09:00。
- 没说出发点，默认城市中心或热门商圈。
- 没说具体口味，先用画像和 POI 标签推荐。

好的澄清应该短，只问一个最关键问题：

```text
想在哪个城市或区域玩？我确认地点后就能先给你出一版路线。
```

不建议：

```text
请告诉我城市、人数、预算、出发时间、出发点、交通方式、饮食偏好、是否亲子、是否室内。
```

## A 和 B 的协作边界

B 侧负责路线策略工具，包括：

- POI 召回
- 路线生成
- 路线评分
- 多目标路线
- 局部替换
- 动态重规划

A 侧不要接管 B 的路线算法。A 要做的是把自然语言变成 B 能执行的结构化输入。

例如用户说：

```text
这家餐厅排队 90 分钟，换一家
```

A 应该转成类似：

```json
{
  "event_type": "queue_spike",
  "event_label": "餐厅排队 90 分钟",
  "event_payload": {
    "affected_poi_id": "poi_002",
    "queue_minutes": 90,
    "force_replace": true
  }
}
```

然后交给 B 的 `ReplanService` 执行。

B 不需要理解自然语言，也不需要读取 LLM 输出长文本。B 只消费结构化字段。

## A 和高德路线的关系

高德路线接入的目标是补全真实路段信息，不是让路线策略直接依赖高德原始 JSON。

数据流是：

```text
POI 顺序
  -> AmapService 查询相邻点之间路线
  -> 统一成项目自己的路段字段
  -> 写回 RouteStop
  -> B 用于评分
  -> C 用于地图展示
```

统一后的字段包括：

- `travel_minutes_from_previous`
- `distance_km_from_previous`
- `transport_mode_from_previous`
- `polyline_from_previous`
- `amap_distance_meters_from_previous`
- `amap_duration_minutes_from_previous`
- `route_leg_source_from_previous`

A 侧解释路线时，只能基于这些统一字段，不要直接引用高德原始 JSON。

如果 `route_leg_source_from_previous` 是 `fallback`，说明使用的是本地估算，回复里要避免说得过度确定。

## A 和 C 的协作边界

C 侧主要关心：

- `/api/chat` 返回结构是否稳定。
- 路线卡片字段是否完整。
- `agent_trace` 是否能展示。
- 澄清问题是否能展示。
- fallback/error 是否能被用户看到。

A 侧需要保证常用响应字段稳定：

- `message`
- `need_clarification`
- `clarifying_question`
- `intent`
- `user_profile`
- `routes`
- `agent_trace`

trace 至少要保留：

- `step`
- `label`
- `status`

新增字段时，最好给前端一个可读 label，避免 C 侧展示一堆内部英文 key。

## Agent Trace 要展示什么

trace 不是模型原始推理，也不是装饰性动画。它是系统可观测性。

建议按层展示：

| 层级 | 要展示什么 |
| --- | --- |
| 理解层 | 本轮被识别成什么意图，置信度多少，是否 fallback |
| 状态层 | 保留、新增、修改、删除了什么 |
| 决策层 | 为什么重规划、局部重规划或只回答细节 |
| 工具层 | POI 候选数、路线数量、是否有未满足要求 |
| 回复层 | 是否使用 LLM 总结，是否用了 fallback |

例如用户追加吃饭后，trace 应该能表达：

```text
本轮判断：追加需求
保留：上海、2人、一日游、拍照
新增：meal_stop
决策：重新生成路线
工具结果：生成 3 条路线，其中至少 1 条包含餐饮节点
```

这样前端、后端和路线策略同学都能快速判断：如果结果错了，到底是理解错、状态合并错、路线工具没满足，还是回复总结说错。

## 回复生成原则

用户看到的回复必须基于结构化事实。

事实骨架可以是：

```json
{
  "kept": ["上海", "2人", "一日游", "拍照"],
  "added": ["meal_stop"],
  "route_summary": {
    "distance_km": 5.7,
    "travel_minutes": 35
  },
  "system_status": {
    "route_generation": "done",
    "llm_summary": "fallback"
  }
}
```

用户回复可以是：

```text
我保留了你们上海两人一日游、喜欢拍照的设定，并加入吃饭节点。
这版路线包含拍照点和餐饮休息点，总路程约 5.7 公里，交通约 35 分钟。
```

注意：

- 如果路线工具没生成路线，不能说“已为你生成路线”。
- 如果 `meal_stop` 没满足，不能说“已经安排吃饭”。
- 如果 LLM 不可用，要返回结构化 fallback 文案。
- 如果交通字段来自 fallback，本轮解释要保守。

## 具体策略点

下面这些是 A 侧 Agent 编排里最关键、也最适合对外讲清楚的策略点。它们不是单独的功能点，而是保证多轮对话稳定的判断规则。

### 策略点 1：先判断轮次类型，再决定流程

用户每说一句话，系统第一步不是生成路线，而是判断本轮属于哪种类型。

常见类型：

| 用户话术 | 轮次类型 | 系统动作 |
| --- | --- | --- |
| 上海两人一日游 | `new_plan` | 初始化状态并生成路线 |
| 我还要吃饭 | `add_constraint` | 继承上一轮状态，追加吃饭需求 |
| 换成杭州吧 | `modify_constraint` | 只修改城市，其他字段继承 |
| 少排队一点 | `add_constraint` / 全量重规划 | 更新偏好并重新生成候选路线 |
| 第二个点换个餐厅 | `replace_stop` | 定位目标点并局部替换 |
| 两个地点之间怎么过去 | `route_detail` | 不重规划，只回答交通细节 |

讲解重点：

```text
先路由，再执行。
不同轮次走不同处理链路，避免所有消息都触发重新规划。
```

### 策略点 2：用户未提到的字段必须继承

多轮对话里，用户经常只补充一个小需求。系统不能因为本轮没说城市、人数、预算，就用默认值覆盖上一轮。

例如：

```text
第一轮：上海两人一日游，喜欢拍照
第二轮：我还要吃饭
```

第二轮应该保留：

- 城市：上海
- 人数：2 人
- 时长：一日游 / 8 小时
- 偏好：拍照

只新增：

- 偏好：吃好
- 必须节点：`meal_stop`

讲解重点：

```text
用户没说的不是没有，而是沿用上一轮。
```

### 策略点 3：显式修改优先于历史状态

继承状态不是一成不变。如果用户明确修改某个字段，新值要覆盖旧值。

例如：

```text
换成杭州吧
```

系统应理解为：

- 城市从上海改成杭州。
- 人数、时长、预算、偏好继续继承。
- 不应该把它当成普通聊天。
- 也不应该重新询问人数和预算。

讲解重点：

```text
没提到的继承，明确提到的覆盖。
```

### 策略点 4：追加约束不能改变路线主场景

用户追加一个需求，不代表要改变整条路线主题。

例如：

```text
上海两人一日游，喜欢拍照
我还要吃饭
```

正确结果：

- 仍然是拍照 / citywalk 方向。
- 增加餐饮或休息节点。
- 路线结构像一天安排。

错误结果：

- 变成纯美食路线。
- 连续安排多个餐厅。
- 原来的拍照偏好消失。

讲解重点：

```text
追加吃饭是给原路线加饭点，不是把路线改成美食专题。
```

### 策略点 5：区分“全量重规划”和“局部重规划”

A 侧要负责判断用户是想整体换风格，还是只调整当前路线的一部分。

| 用户表达 | 类型 | 处理方式 |
| --- | --- | --- |
| 更省钱一点 | 全量重规划 | 继承硬约束，重新生成候选路线 |
| 少排队一点 | 全量重规划 | 提高排队权重，重新排序或重生成 |
| 少走路 | 全量重规划 | 调整距离和交通策略 |
| 这家餐厅排队 90 分钟 | 局部重规划 | 只替换受影响餐厅 |
| 第二站换掉 | 局部重规划 | 只替换目标站点 |
| 下雨了怎么办 | 局部重规划 | 优先替换后续室外点 |

讲解重点：

```text
整体偏好变化走全量重规划。
指向当前路线某个点或现实事件，走局部重规划。
```

### 策略点 6：路线细节追问不触发路线生成

如果用户是在问当前路线的原因、交通、费用或注意事项，系统应该只回答问题。

例如：

```text
第二站怎么过去？
为什么推荐这家？
这条路线大概走多久？
```

系统应该：

- 读取当前路线。
- 使用已有 `RouteStop` 交通字段、评分理由和 POI 信息回答。
- 不重新召回 POI。
- 不重新生成路线。

讲解重点：

```text
问细节就是解释当前结果，不是重新做一遍规划。
```

### 策略点 7：只在必要时澄清

Agent 不应该把聊天变成问卷。只有缺少关键字段，导致无法生成可执行路线时，才追问。

必须澄清：

- 城市缺失。
- 目标过泛。
- 意图不清。
- 局部替换无法定位目标点。

可以默认：

- 人数默认 1 人。
- 预算默认中等。
- 出发时间默认 09:00。
- 出发点默认城市中心或热门商圈。

讲解重点：

```text
能先出一版就先出一版。
只问最影响执行的一个问题。
```

### 策略点 8：把“隐含需求”和“必须包含”分开

一日游通常需要饭点和休息点，这是系统可以根据常识加入的隐含需求。但用户明确说“我要吃饭”后，饭点就从建议项升级成必须项。

区别：

| 类型 | 含义 | 路线工具要求 |
| --- | --- | --- |
| `implicit_needs: ["meal_stop"]` | 建议安排饭点 | 优先满足 |
| `must_include: ["meal_stop"]` | 用户明确要求吃饭 | 至少一条主推路线必须满足 |

讲解重点：

```text
默认饭点是建议，用户明确说了就是承诺。
```

### 策略点 9：工具结果优先，LLM 不编造事实

A 侧回复必须基于结构化工具结果。

可以引用：

- `Route.summary`
- `Route.reasons`
- `Route.score_breakdown`
- `RouteStop.reason`
- `travel_minutes_from_previous`
- `distance_km_from_previous`
- `route_leg_source_from_previous`
- `changed_stops`
- `live_warnings`
- `replan_reason`

不能让 LLM 自己编：

- 新 POI。
- 新价格。
- 新交通时间。
- 新路线距离。
- 高德没有返回的路段细节。

讲解重点：

```text
LLM 负责把事实说清楚，不负责创造事实。
```

### 策略点 10：fallback 和失败必须可见

真实系统里 LLM、高德、路线工具都可能失败。失败不是问题，隐藏失败才是问题。

必须进入 trace 的情况：

- LLM 解析失败，使用 fallback。
- LLM 总结失败，使用结构化文案。
- 高德没有 key 或请求失败，使用本地估算。
- `must_include` 没有被满足。
- POI 召回为空。
- 路线生成为空。

讲解重点：

```text
系统可以降级，但不能假装没降级。
```

### 策略点 11：trace 要能定位是哪一层出错

trace 应该帮助我们判断问题发生在哪里。

| 问题表现 | 应检查的 trace 层 |
| --- | --- |
| 用户意思理解错 | `understanding` |
| 上下文丢失 | `state_merge` |
| 不该重规划却重规划 | `planning_policy` |
| 路线没有饭点 | `tool_result` |
| 回复说了不存在的内容 | `response_composer` |

讲解重点：

```text
trace 不是展示“模型想了什么”，而是展示系统每层做了什么。
```

### 策略点 12：字段契约稳定，A/B/C 各守边界

A、B、C 三侧协作时，字段稳定比单点实现更重要。

A 侧要守住：

- 自然语言理解和状态管理在 A。
- 路线策略和评分在 B。
- UI 展示在 C。
- 高德原始返回由 `AmapService` 消化，不透传给 B/C。
- API 字段变化必须同步 schema、前端类型和接口文档。

讲解重点：

```text
Agent 可以复杂，但对外契约要稳定。
```

## 一个完整例子

### 第一轮

用户：

```text
上海两人一日游，喜欢拍照
```

系统理解：

```json
{
  "turn_type": "new_plan",
  "hard_constraints": {
    "city": "上海",
    "people_count": 2,
    "duration_hours": 8
  },
  "soft_preferences": ["拍照"],
  "implicit_needs": ["meal_stop", "rest_stop"]
}
```

系统行为：

- 初始化 `TripState`。
- 调用 POI 召回。
- 调用路线生成。
- 返回路线和 trace。

### 第二轮

用户：

```text
我还要吃饭
```

系统理解：

```json
{
  "turn_type": "add_constraint",
  "inherit_previous": true,
  "intent_delta": {
    "added_preferences": ["吃好"],
    "added_must_include": ["meal_stop"]
  }
}
```

状态合并：

```text
保留：上海、2人、一日游、拍照
新增：吃好、meal_stop
```

系统行为：

- 继承原来的城市、人数、时长、拍照偏好。
- 把 `meal_stop` 升级为必须包含。
- 重新生成路线。
- trace 中记录保留和新增。

正确回复：

```text
我保留了上海两人一日游和拍照偏好，并把吃饭作为必须安排的节点加入路线。
```

错误做法：

```text
重新给你安排一条美食路线。
```

因为用户只是追加吃饭，不是要把路线主题改成纯美食。

## 推荐实施顺序

### 第一阶段：先把多轮状态做稳

目标：

- 不丢城市、人数、时长、预算。
- 不乱覆盖原偏好。
- 追加、修改、删除都能解释成 delta。

重点：

- `MessageRouter`
- `QueryUnderstanding`
- `IntentDelta`
- `TripState`
- `apply_query_delta`
- trace 的 `kept / added / changed / removed`

### 第二阶段：让路线工具消费结构化需求

目标：

- `soft_preferences`
- `implicit_needs`
- `must_include`
- `meal_stop`
- `rest_stop`

这些字段进入路线 planner request，而不是只靠关键词。

### 第三阶段：支持围绕当前路线持续编辑

目标：

- 选择路线。
- 替换某个点。
- 删除某个点。
- 锁定某个点。
- 根据排队、堵车、下雨、累了等事件局部重规划。

### 第四阶段：做可评估 Agent

目标：

- 不只看回复像不像。
- 要能判断理解层、状态层、工具层、回复层哪个错了。
- demo case 做成分层断言。

## 核心验收 case

### 1. 追加吃饭不丢上下文

```text
上海两人一日游，喜欢拍照
我还要吃饭
```

期望：

- 仍然是上海。
- 仍然是两人。
- 仍然是一日游。
- 仍然保留拍照偏好。
- 新增 `meal_stop`。
- 路线里至少一条包含餐饮/休息节点。

### 2. 路线追问不重新规划

```text
两个地点之间怎么过去
```

期望：

- 识别为 `route_detail`。
- 不重新召回 POI。
- 不重新生成路线。
- 基于当前路线交通字段回答。

### 3. 修改城市只改城市

```text
换成杭州吧
```

期望：

- 识别为 `modify_constraint`。
- 城市变成杭州。
- 人数、预算、时长等未提到字段继承。

### 4. 更省钱不覆盖硬预算

```text
更省钱一点
```

期望：

- 识别为整体偏好变化。
- 增加省钱目标。
- 不把具体预算随便改成另一个默认值。

### 5. 换一家走局部重规划

```text
第二个点换个餐厅
```

期望：

- 识别为 `replace_stop`。
- 只替换第二个点。
- 当前路线中其他点尽量保留。

## 这部分最容易踩的坑

### 1. 让 LLM 直接决定一切

这样会导致上下文覆盖、过度重规划和编造事实。LLM 应该只负责理解和表达，关键流程由后端显式控制。

### 2. 继续只维护 `last_intent`

`last_intent` 可以短期兼容，但不能作为唯一状态源。长期要靠 `TripState` 维护完整上下文。

### 3. 把所有偏好都塞进 preferences

“拍照”“少排队”“吃饭”“必须安排饭点”不是同一种东西。需要区分硬约束、软偏好、隐含需求和必须包含。

### 4. trace 只展示好看的步骤

trace 要能定位问题。fallback、error、未满足要求、状态变化都必须可见。

### 5. 路线解释编造细节

A 的回复必须基于 B 的路线结果、高德统一字段和结构化评分，不要让 LLM 自己补地点、时间、价格。

### 6. 随意改 API 字段

`/api/chat`、Route、Intent、Trace 字段会影响 C 侧展示。字段变更必须同步 schema、前端类型和接口文档。

## 最后总结

A 侧这部分本质上是在做 Agent 的“脑干”和“记忆系统”：

- 听懂用户这一轮说了什么。
- 记住上一轮已经确定的旅行上下文。
- 判断本轮该走哪条流程。
- 把自然语言转成工具能执行的结构化请求。
- 基于真实工具结果生成回复。
- 用 trace 让整个过程可解释、可调试、可回归。

只要这条主线站稳，B 侧路线策略和 C 侧前端体验就能在稳定契约上继续迭代。
