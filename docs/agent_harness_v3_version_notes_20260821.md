## 1. 版本结论

这次升级有效，但还不应直接替换稳定版本。

在同一套 30 条能力评测集上，严格通过率从 **43.3%（13/30）提升到 80.0%（24/30）**，平均分从 **79.2 提升到 97.7**，未捕获异常从 **3 个降到 0 个**。最终剩余的 6 个失败全部收敛为“没有生成足够路线”，不再混杂状态崩溃、错误追问、偏好漏识别或评测器误判。

这说明本次优化不只是让若干 Query 碰巧通过，而是把问题边界从“Agent 各层同时不稳定”收敛到了“路线可行性与最终选路”这一层。后续可以集中改路线约束口径，而不需要继续在意图 Prompt 里堆特例。

## 3. 为什么这版能提升

### 3.1 在系统边界吸收模型输出差异

模型有时把起点输出为字符串，有时输出为结构体。旧实现把这种格式波动直接交给 Reducer，导致 Pydantic 异常；当前版本在模型边界统一转换成 `LocationRef`，使后续状态层只接收稳定类型。

这类修复覆盖所有地点表达，不依赖“国贸”“春熙路”等具体地点。直接效果是评测中的未捕获异常从 3 个降为 0。

### 3.2 把“模型觉得不确定”和“产品必须追问”分开

旧 Policy 会把所有 ambiguity 都当作阻断问题，因此“半日游”“附近”“已有 GPS”也可能触发追问。现在 ambiguity 具有类型，Policy 只对以下情况阻断：

- 缺少规划必需字段且没有可靠默认来源；
- 用户明确硬约束互相冲突；
- 必须获得用户授权才能放宽的约束。

其他不确定项使用产品默认值继续规划，并在结果中说明。这减少了无意义追问，也防止模型的一句保守提示改变整个控制流。

### 3.3 隐式需求从散落 Prompt 规则变成单一领域引擎

饭点需求过去同时存在于 Prompt、fallback 和路线逻辑中，容易重复推断或互相覆盖。当前新增 `ContextualNeedEngine`，以行程时间窗和用户明确否定为输入，统一判断午餐、晚餐等上下文需求。

模型仍负责理解“已经吃过了”“只喝咖啡”等语义，但是否形成路线必需角色由确定性引擎裁决。这样可以覆盖所有跨饭点行程，而不是逐句添加正则。

### 3.4 对每种槽位做语义校验

旧 fallback 可能把“别走太多路”误识别为商圈，说明抽到文本不等于抽对了字段。当前地点提取要求地点证据或位置介词；出行强度、兴趣、避雷分别进入自己的 taxonomy。

状态字段因此不再只是“有值”，而是“值符合该字段的语义契约”。

### 3.5 用 canonical taxonomy 统一理解、规划和评测

“夜景/看夜景”“少走路/轻松不累”等同义表达过去在 Agent、路线目标和评测器里使用不同文字，造成真实能力与评分同时失真。当前先把原始表达归一到 canonical 标签，再由状态、工具和评测共享这些标签。

这一步将偏好缺失从 8 个降为 0，说明提升来自统一语义协议，而不是为某条评测写答案。

### 3.6 恢复动作由失败诊断驱动

旧实现遇到零路线后倾向于机械扩大召回，即使真正原因是三站约束、营业时间、预算或总时长。当前执行器读取工具诊断，在候选充足但组合无解时按 `3 → 2 → 1` 降低最少站点，并要求下一次调用必须有参数变化或新证据。

这使路线不足从 13 个降到 6 个，同时把重复调用限制在有意义的恢复路径内。

### 3.7 评测器按业务终态评分

`infeasible` 是一种有效、可解释的规划终态，不等于系统没有输出。当前评测器识别 `complete / partial / infeasible / degraded`，并记录状态、工具、诊断和路线数量。

因此分数的变化能够反映 Agent 真实变化，失败也能定位到理解、状态、决策、工具、恢复或路线验证中的具体一层。

## 4. 本次实现范围

- 类型化 ambiguity 和旧格式兼容。
- 字符串地点到 `LocationRef` 的边界归一化。
- 只对阻断问题追问的确定性 Policy。
- 基于时间窗的 `ContextualNeedEngine`。
- 地点槽位语义校验与 canonical 偏好补全。
- 诊断驱动的 `3 → 2 → 1` 路线恢复。
- V2 终态、观察信息和失败原因的评测支持。
- 30 条六维能力数据集、批量运行器和完整 JSON 结果留档。

保留的既有能力：LYNN 召回与排序、多目标 Fine Rank、现有 POI/路线/地图服务、`/api/chat`、流式接口和 V1 兼容路径。

## 5. 当前剩余问题

最终 6 个失败均为路线数量不足：

1. 显式城市覆盖请求默认城市。
2. 聚餐人数识别后的路线生成。
3. 未指定起点时使用上海 GPS。
4. 咖啡需求不替代正餐。
5. 北京低预算路线。
6. 北京亲子轻松路线。

这些 Case 的共同点不是“没理解”，而是上游状态基本正确、下游没有返回合法路线。下一步应统一候选生成、营业时间、预算、时长和最终选择的约束口径，并建立最终选路不变量；不应继续给理解 Prompt 添加这些 Query 的特判。


```powershell

```

```powershell
.\backend\.venv\Scripts\python.exe scripts\run_agent_v2_capability_eval.py --repeat-count 3 --case-timeout 60
```

代码回退可以直接切回基线分支 `keykii`；运行时回退使用 `AGENT_RUNTIME_VERSION=v1`。本版本未删除 V1、LYNN 或原有服务，因此回退不需要迁移用户数据。
