# 路线规划逻辑 Introduction

最后同步：2026-08-23。

这份文档用于向 A 同学和 B 同学介绍当前路线规划系统的整体逻辑：数据从哪里来、用户需求如何变成策略目标、POI 如何推荐排序、路线如何生成、交通路段如何补全，以及路线如何评分、修改和预制。

核心原则一句话：

> LLM 负责理解用户需求和解释结果，路线顺序和 POI 选择由确定性策略系统完成，这样才能稳定控制预算、营业时间、距离、必去点、避雷和路线差异。

## 1. 整体链路

普通路线规划的主链路是：

```text
用户消息
-> Agent 解析 Intent
-> 读取 UserProfile
-> 生成策略标签和路线目标
-> POI 多路召回、过滤、粗排、精排
-> RouteService 生成候选路线
-> 补交通路段
-> 约束检查和路线评分
-> RouteRerankService 选最终三条
-> Agent 解释路线
```

为什么这样分工：

- LLM 擅长理解自然语言，但不适合稳定处理大量 POI 的组合搜索。
- 路线规划有硬约束，比如营业时间、最晚入场、必去点、避雷和总时长，必须由策略系统控制。
- 策略链路可以测试、评测、灰度，比纯 prompt 更可控。

## 2. 数据 Mock

当前数据主要是 mock 和 seed 数据，用于演示、离线评测和策略验证。

核心数据包括：

- POI 数据：`data/seed/pois.json`
- 用户画像：`data/seed/user_profiles.json`
- 用户行为：`data/seed/interaction_events.json`
- mock 天气：`data/seed/mock_weather.json`
- 协同过滤产物：`data/models/cf/item_similarity.json`
- 双塔 embedding：`data/models/two_tower/`
- POI 精排模型：`data/models/fine_rank/`

当前 POI 覆盖上海和北京，每个城市约 1000 多个 POI，覆盖 17 个类目。POI 不只包含 `category`，还补充了路线规划需要的结构化字段：

- `primary_category`：主类目，例如 food、culture、landmark。
- `secondary_categories`：辅助类目，例如 photo、indoor、night、rainy。
- `route_roles`：路线角色，例如 main_activity、meal、coffee_break、rest_stop、photo_stop、night_end。
- `experience_tags`：体验标签，例如 文艺、安静、夜景、亲子。
- 营业、最晚入场、停留时长、排队、人流、价格、步行强度等。

为什么要 mock：

- 让策略可以离线稳定复现，不依赖真实地图和线上流量波动。
- 让评测集可以固定，方便比较候选规模、召回、Beam、重排等模块。
- 方便 A/B/C 在没有真实外部服务时联调完整体验。

需要说明的边界：

- mock 地图不是精确导航。
- mock 用户行为不能代表真实用户效果。
- Mock P95 只代表算法和 mock 地图环境性能，真实高德延迟需要单独监控。

## 3. 策略标签和路线目标

用户一句话会被解析成 `Intent`，包括城市、时间、时长、预算、偏好、避雷、必去点、区域等。系统还会读取 `UserProfile`，包括长期偏好、预算敏感度、步行耐受、人群耐受、喜欢和不喜欢的 POI。

`StrategyService` 会把这些信息转成两类东西：

- 策略标签：例如 少走路、省钱、吃好、拍照、雨天、夜景、少排队。
- 路线目标 objective：决定本次要生成哪几种路线。

常见 objective：

| objective | 含义 | 典型场景 |
| --- | --- | --- |
| `balanced` | 综合平衡 | 默认兜底 |
| `budget` | 省钱 | 低预算、高性价比 |
| `low_walking` | 少走路 | 老人、亲子、轻松 |
| `food_first` | 美食优先 | 吃好、咖啡、小吃 |
| `photo_food` | 拍照 + 餐饮 | 出片餐厅、拍照咖啡 |
| `nature_relax` | 自然放松 | 公园、自然风景 |
| `photo_citywalk` | 拍照 citywalk | 街区、地标、拍照 |
| `indoor_rainy` | 雨天室内 | 雨天、高温、室内 |
| `night_friendly` | 夜间友好 | 夜景、晚上可玩 |

普通规划通常选择两个最相关 objective，再补一个 `balanced`。

为什么要有 objective：

- 同一个 POI 对不同路线目标价值不同。
- 省钱路线更关心价格，少走路路线更关心距离，美食路线更关心餐饮质量。
- 如果只用一个综合目标，特殊需求很容易被平均掉。

口语讲法：

> objective 就是路线的“方向”。用户说少走路，我们就不能只给热门景点；用户说吃好，我们就要让餐饮节点在候选里有更高优先级。

## 4. 推荐排序模型

推荐排序模型负责从城市 POI 中找到适合本次路线的候选点。它不是一步排序，而是一个漏斗：

```text
城市 POI
-> 过滤
-> 多路召回
-> RRF 融合
-> 粗排
-> objective 精排
-> 交给路线生成
```

### 4.1 多路召回

召回阶段会从多个角度找 POI：

- 内容召回：匹配用户偏好、类目、标签、搜索文本。
- 画像召回：匹配用户长期类目偏好、角色偏好、体验偏好。
- 协同过滤召回：根据历史行为找相似 POI。
- 双塔召回：用 user/poi embedding 找语义相关 POI。
- 场景召回：补雨天、夜间、少走路、美食、拍照等场景点。
- 路线角色召回：补主活动、餐饮、休息、拍照、交通锚点、夜间收尾。

多路召回使用 RRF 融合：

```text
rrf_score = sum(channel_weight / (60 + rank))
```

为什么不用直接加分：

- 不同通道分数值域不同，直接相加不稳定。
- RRF 更关注每个通道的排名贡献，融合更稳。

### 4.2 过滤

过滤分三层：

- 城市和区域过滤：优先保证 POI 在目标城市和指定区域。
- 偏好与避雷过滤：保留匹配偏好的点，排除明确 avoid_tags。
- 极端预算过滤：轻微超预算可以扣分保留，极端超预算直接排除。

为什么这么做：

- 硬条件不能靠后续排序“扣回来”。
- 但一般预算或偏好不应太早硬删，否则候选池会过窄。

### 4.3 粗排

`CoarseRankService` 用轻量规则快速筛掉明显不合适的点。主要看：

- 质量：评分、评论量、热度。
- 排队：排队时间、人流强度。
- 距离：离起点或当前区域远不远。
- 预算：价格是否贴合。
- 偏好：是否命中用户偏好和策略标签。
- 时间：营业时间、最晚入场、适合时段。
- 风险：是否命中避雷或风险标签。

为什么要粗排：

- 多路召回池比较大，不能直接让路线搜索处理所有 POI。
- 粗排成本低，适合先做一轮大范围筛选。

### 4.4 精排

`FineRankService` 使用离线训练的 sklearn 表格模型，分别预测：

- `p_click`
- `p_like`
- `p_skip`

最终得到 POI relevance：

```text
poi_relevance_score = 0.4*p_click + 0.5*p_like - 0.3*p_skip
```

精排会按 objective 单独计算：

```text
poi_relevance_scores_by_objective[objective][poi_id]
```

为什么要精排：

- 粗排主要是规则，速度快但表达能力有限。
- 精排可以利用用户画像、POI 特征、历史交互和 objective 特征。
- 分 objective 精排能避免所有路线都变成 balanced。

## 5. 路线生成逻辑

路线生成负责把候选 POI 变成多条可执行的路线候选。

核心流程：

```text
每个 objective 的 POI 候选池
-> 选多个 start seed
-> Beam Search 扩展路线状态
-> 检查时间、营业、必去、角色和预算
-> 生成每个 objective 的候选路线
-> 汇总所有 objective 候选
```

Beam 状态会记录：

- 已选 POI
- 当前时间和已耗时
- 当前坐标
- 累计费用、交通、排队
- 未完成的必去点
- 未覆盖的必要路线角色
- 当前近似分

搜索时会检查：

- 不能超总时长。
- 到达时必须营业。
- 不能晚于最晚入场。
- 必去点不能漏。
- 明确避雷不能碰。
- 极端预算不能进。
- 路线结构要合理，不能无意义地全是同类点。

为什么用 Beam Search：

- 路线是组合问题，前一站会影响后一站。
- 贪心只看当前最高分，容易局部最优。
- Beam Search 同时保留多条候选路径，更容易兼顾质量和可行性。

路线不足时有受控降级：

- 先放宽路线间普通 POI 重合限制。
- 再允许两站轻量路线。
- 必去点、营业时间、城市区域、避雷和极端预算不自动放宽。

## 6. 交通路段逻辑

交通路段逻辑负责把 POI 顺序变成真正可执行、可展示的路线。

每个 stop 会补充“从上一个位置到当前 POI”的路段字段：

- `travel_minutes_from_previous`
- `distance_km_from_previous`
- `transport_mode_from_previous`
- `polyline_from_previous`
- `route_steps_from_previous`
- `route_leg_source_from_previous`

交通计算分两阶段：

```text
搜索阶段：用近似距离和缓存交通时间
最终候选阶段：只给高分路线补详细交通路段
```

为什么分两阶段：

- Beam Search 会尝试很多组合，不能每扩展一步都请求地图。
- 先用近似交通保证搜索速度。
- 最终候选再补详细路段，保证前端可展示、评分可校验。

交通方式不是简单选最快，而是结合：

- 距离远近
- 用户是否少走路
- 是否亲子、老人、轻松场景
- 是否夜间
- POI 推荐交通方式
- 公共交通是否绕路

当前 Mock 地图支持步行、地铁、公交、打车。如果真实地图不可用，会 fallback 出一段可读交通说明，避免路线断掉。

为什么这么做：

- 用户需要的是可执行路线，不只是 POI 顺序。
- 交通时间会影响总时长、距离评分、可靠性和 warning。
- Mock 地图让离线评测可复现。

## 7. 路线最终评分

路线候选生成后，会进入 `ConstraintEvaluator` 和 `ScoringService`。

`ConstraintEvaluator` 区分硬约束和软约束：

- 硬约束决定能不能用，例如闭店、晚于最晚入场、超总时长、漏必去点、命中明确避雷。
- 软约束决定好不好，例如轻微超预算、步行长、排队多、雨天户外、跨区域跳点。

`ScoringService` 输出五维分：

| 维度 | 含义 |
| --- | --- |
| quality | POI 质量 |
| queue | 排队和拥挤 |
| budget | 预算匹配 |
| distance | 交通距离和步行强度 |
| preference | 用户偏好和 objective 匹配 |

路线还会补充：

- `p50_duration_minutes`
- `p80_duration_minutes`
- `buffer_minutes`
- `reliability_score`
- `risk_level`
- `warnings`

最后 `RouteRerankService` 会从所有候选里统一选三条。它考虑：

- 路线基础分
- POI 精排均值
- 结构完整性
- objective 匹配
- 交通效率
- 可靠性
- 预算和排队风险
- 路线间重合率

为什么要最终重排：

- POI 好不等于整条路线好。
- 每个 objective 的第一名放在一起，不一定是最好的三条组合。
- 三条路线要有差异，但不能为了差异牺牲明显质量。

## 8. 修改路线

修改路线指用户已经拿到路线后，又提出局部变化，例如：

- “换掉第二站”
- “这个太远了”
- “下雨了”
- “排队 90 分钟”
- “我累了，少走路一点”
- “这家关门了”

重规划入口是 `ReplanService`。它不是默认推倒整条路线，而是优先做局部修改：

```text
找到受影响 stop
-> 保留已完成和锁定节点
-> 为受影响位置召回替代 POI
-> 用局部 Beam 组合替代方案
-> 重建后续时间和交通
-> 重新评分和重排
```

替代 POI 会考虑：

- 同城市
- 不在已完成、锁定、避雷集合中
- 和原 POI 在角色、主类目、体验标签、适合时段上相近
- 当前偏好，比如少走路、室内、低排队
- 营业和预算是否可行

为什么这么做：

- 用户通常只想改局部，不想整条路线全部变掉。
- 已完成节点和锁定节点必须保留。
- 局部修改比全量重算更稳定，也更符合用户预期。

## 9. 预制路线

预制路线是用户正式交互前，根据城市、mock 天气和画像提前生成 1-3 条路线。

入口是 `PredictiveRouteService.generate()`。

流程：

```text
user_id + city + weather_scenario
-> 读取 mock 天气
-> 天气转偏好
-> 合并用户画像
-> 选择 objectives
-> POI 召回和精排
-> 为每个 objective 生成候选路线
-> 做差异过滤
-> 返回预制路线
```

天气会影响偏好：

- 雨天、大风：室内、少走路。
- 高温：室内、咖啡、少走路。
- 晴天或舒适阴天：citywalk、拍照、自然风景。
- 夜间：夜景、晚上可玩。

为什么要预制路线：

- 页面初始化时可以更快展示候选。
- 新用户也能看到可用路线，不必等完整对话。
- 画像用户可以提前得到更个性化的路线。

边界：

- 预制路线当前主要是后端服务能力，还不是完整正式 API。
- 预制路线依赖 mock 天气和 mock 地图，适合演示和冷启动体验。

## 10. 反馈、评测和发布保护

路线曝光和用户反馈会写入 SQLite：

- 曝光：记录 request、algorithm_version、路线位置、objective、score、POI 组成。
- 反馈：记录选择、替换、完成、退出、评分等事件。

路线级模型目前默认关闭。只有满足以下条件后才允许训练和启用：

- 至少 10,000 次曝光。
- 至少 1,000 次选择。
- 覆盖至少 7 天。
- 按时间切分评估。
- 相比规则重排在 NDCG、选择率代理指标和校准误差上有提升。

当前离线评测有 120 个固定案例：上海 60 个、北京 60 个。

当前工作区最新报告 `artifacts/route-strategy/route_strategy_evaluation.md` 的结果：

| 指标 | 结果 |
| --- | ---: |
| 可行路线率 | 100% |
| 三路线生成率 | 100% |
| 硬约束违反数 | 0 |
| 必去 POI Recall | 100% |
| 最终路线必去遗漏数 | 0 |
| 必要角色覆盖率 | 100% |
| 非必去 POI 平均重合率 | 7.82% |
| Mock P95 | 1772.92ms |

发布开关：

```text
PLANNING_PIPELINE_MODE=legacy|shadow|v2
PLANNING_PIPELINE_ROLLOUT_PERCENT=0..100
```

未显式配置时默认使用 V2；`PLANNING_PIPELINE_ROLLOUT_PERCENT` 再按 user/session hash 做确定性灰度，可配置 10%、50%、100% 放量。`shadow` 仍可显式用于只观测、不切流。

为什么这么做：

- 不能只凭 demo 判断策略好坏。
- 不能伪造真实路线模型效果。
- 策略发布需要可回退、可灰度、可评测。

## 11. 给 A 和 B 的讲法

对 A 同学重点讲：

- Agent 负责理解和解释，不直接决定 POI 顺序。
- `/api/chat` 核心接口兼容。
- `debug=true` 可以看到召回、精排、Beam、降级、重排诊断。
- 普通用户不展示模型概率、内部权重和技术错误。

对 B 同学重点讲：

- POI 结构化字段非常关键，尤其是路线角色、体验标签、营业时间、价格、排队和步行强度。
- 多路召回、粗排、精排、Beam、评分、重排是一条完整漏斗。
- 后续优化优先看评测分桶和消融实验，不只看单个 demo。
- 路线级模型要等真实反馈数据，不会默认启用。

## 12. 推荐口头讲解顺序

如果只讲 5 分钟，可以按这个顺序：

1. 先讲整体链路：LLM 理解需求，策略系统规划路线。
2. 讲数据 mock：POI、画像、行为、天气、地图都是可复现的 seed/mock。
3. 讲策略标签和 objective：把自然语言偏好变成路线目标。
4. 讲推荐排序：多路召回、过滤、粗排、精排。
5. 讲路线生成：Beam Search 做受约束组合搜索。
6. 讲交通和评分：补路段、算五维分、做最终路线重排。
7. 讲修改路线和预制路线：分别解决动态调整和冷启动。
8. 最后讲验收和边界：固定 120 案例、Mock P95、真实模型暂不启用。

可以用这段作为开场：

> 当前路线规划不是让 LLM 直接编路线，而是把用户需求解析成结构化 Intent，再交给策略系统做 POI 推荐、路线搜索、交通补全、评分和重排。这样路线既能满足用户偏好，也能控制营业时间、预算、距离、必去点和路线差异。

可以用这段作为结尾：

> 所以这套系统本质上是一条完整的路线规划流水线：前面用推荐模型找到好 POI，中间用 Beam Search 生成可执行路线，后面用约束评分和路线重排选最终三条。短期用 mock 和固定评测保证稳定，长期再接真实反馈做路线级学习。
