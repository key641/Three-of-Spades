## 一、产品背景与核心命题

### 1.1 我们在解决什么问题

用户在周末或本地游场景下的出行决策链路，通常是这样的：

> 打开小红书刷攻略 → 翻大众点评查评分 → 发朋友圈问推荐 → 东拼西凑手动串联 → 随便定个地方出发

核心痛点并不是"找不到信息"，而是 **信息碎片化、拼接成本高**。用户需要自己回答"去哪""怎么排序""花多少钱""时间够不够"，然后把这些答案手动连成一条可执行的路线，这个过程耗时且容易放弃。

本产品的核心切入点：**用一句自然语言，替代上述整个决策过程**。你说"上海半天带娃，预算 200"，AI 直接返回一条可执行的行程方案，并支持实时调整。

### 1.2 产品定位

```
自然语言输入 → AI 自动规划 → 用户查看 & 调整 → 出发执行 → 沉淀反馈
```

目标是做一个**出行决策的完整闭环**，而不只是"推荐去哪里"的内容工具。

## 二、功能模块全览

从用户视角，整个产品由以下模块构成：

### 2.1 用户偏好引导（Onboarding）— 个性化系统的入口

**这是什么**：用户首次进入 App 时的 2 步引导配置，用于建立"个人出行档案"。

**具体功能点**：
- **Step 1 · 出行场景选择**：用户从 9 个场景中多选自己平时的玩法，包括：街头漫游、美食探店、文化艺术、演出活动、热门景点、亲子家庭、自然放松、逛街购物、随心而行。每个场景都附有简要说明（如"街头漫游：咖啡馆、集市、新店探索"），降低选择门槛。
- **Step 2 · 出行偏好 & 禁忌设置**：分为两部分：
  - "我喜欢"部分按 4 个维度分组展示标签：时间效率（少排队、节奏慢、特种兵…）、出行方式（公交方便、步行 citywalk、自驾…）、消费偏好（性价比高、体验优先…）、体验风格（人少景美、适合拍照、小众特色…）
  - "我想避开"部分展示 7 个反向过滤标签（人太多、消费贵、需要排队、距离太远等）
  - 两个部分均支持"+ 自定义"输入，用户可以填写预设选项里没有的偏好

**数据流向**：用户填写完毕后，所有偏好信息存入本地（`localStorage`），并在每次规划请求中随请求一起发送给后端，作为路线打分和排序的权重依据。

**体验设计要点**：
- 顶部有进度条（第 1 步 / 共 2 步），让用户知道流程有多长
- 步骤之间有返回按钮，允许修改上一步
- 完成时有 2 秒的"正在保存偏好…"加载动效，强化"已记住你"的仪式感
- 页面整体是滚动式，不是 Dialog 弹窗，避免移动端键盘遮挡问题

### 2.2 首页（Home）— 发现入口 & 个性化推荐

**这是什么**：完成 Onboarding 后进入的主界面，是用户每次开启规划的起点。

**具体功能点**：

#### 2.2.1 个性化问候 & 用户标识
- 顶部展示基于时间的动态问候语（早上好 / 下午好 / 晚上好），并带上用户昵称（如"下午好，小明"）
- 右上角有头像按钮，图标取自用户 Onboarding 时选的第一个出行场景 emoji（如选了"美食探店"则显示 🍜），点击进入个人主页

#### 2.2.2 定位 & 天气状态条
- 展示当前位置（如"北京市西城区西单"）和实时天气（如"☀️ 晴 28°"）
- 定位逻辑分为三个阶段：先显示默认位置（西单，作为 Demo 起点）→ 如用户授权则调用 GPS 获取真实位置 → 再异步通过 Nominatim 逆地理编码获取更精确的街道级地址
- 定位失败时有明确提示（"位置已拒绝，点击重试"）

#### 2.2.3 自然语言输入框（核心入口）
- 居中的多行输入框，占位提示举了具体例子（"随便说说，比如「朝阳半天 citywalk，预算100」…"），示范式引导降低输入门槛
- 支持回车直接发送（桌面端适配）、"开始规划"按钮触发
- 输入框高度随内容自适应增长（最高 100px）

#### 2.2.4 弹幕推荐问句（降低冷启动门槛）
- 输入框下方有一行轮播的示例问句，按当前时段动态生成不同内容：
  - 早上：「一早好！帮我前面找个早食小居吧」「今天天气不错，适合来一场晨跑路线」
  - 下午：「下午了，附近有什么适合拍照的地方？」「帮我找几个人少景美的打卡点」
  - 晚上：「推荐个适合聚餐的餐厅，6 人左右」「夜幕下适合散步的地方，要有夜景」
- 支持左右拖拽切换，8 秒自动轮播，点击直接填入输入框并聚焦

#### 2.2.5 猜你喜欢（基于偏好的精选路线推荐）
- 根据用户 Onboarding 中填写的场景偏好 + 当天天气，从预设路线库中推选 3 条路线
- 每张卡片显示：路线封面图（支持多图左右滑动切换）、推荐理由标签、起终时间、人均费用、站点流（彩点连线展示经过的 POI 序列）、时间进度条
- 点击卡片进入路线详情覆盖页，可直接"用这条路线"（跳转到规划页并预填对应提示词）

### 2.3 规划页（Planner）— 核心交互场景

**这是什么**：用户完成 Onboarding 后，发起规划请求进入的主要工作区，是整个产品体验的核心。

整体布局是"地图全屏背景 + 底部可拖拽面板"，面板内承载对话、路线方案、设置等所有内容。

#### 2.3.1 行程配置面板（Onboarding 后首次进入时展示）

用户进入规划页后，首先看到一个结构化的行程配置区，可以在发起规划前设置基本参数：

- **出行人数**：图标 + 数字，支持 +/- 调整（1~12 人）
- **出行时段**：上午 / 下午 / 晚上 / 全天 四个选项
- **今天想玩什么**：根据用户 Onboarding 偏好预填，可修改（多选场景 tag）
- **预算档位**：不限 / 经济（人均 < ¥50）/ 适中（人均 < ¥150）/ 享受（人均 < ¥300）

用户直接输入自然语言跳过配置面板时，配置面板收起，AI 根据对话内容推断这些参数。

#### 2.3.2 对话面板（Chat）

规划核心交互区，展示完整的对话历史：

- **用户气泡**：右侧对齐，深色背景
- **AI 回复气泡**：左侧对齐，含文字回复 + 路线卡片（如有）
- **追问气泡**：当 AI 无法明确判断用户意图时，会在回复中插入追问（如"请问你更在意省钱还是少排队？"），用户回复后继续规划
- **输入栏**：底部固定，支持自然语言输入，同时有快捷功能区（语音入口位置预留、发送按钮）

#### 2.3.3 AI 思考过程（Agent Trace）

每次规划请求发出后，在 AI 回复出现之前，实时展示推理步骤：

- **展示形式**：默认折叠为一行摘要（"正在分析你的需求… 3 步"），点击展开看详情
- **推理链内容**：包括意图理解（"识别到 citywalk 需求，时长 4 小时"）→ 偏好读取（"检索你的偏好：少排队、步行"）→ POI 召回（"找到 12 个候选地点"）→ 路线生成（"生成 3 条路线方案"）等步骤
- **状态标识**：每个步骤有 loading / 完成 / 警告 三种状态图标
- **手机端友好**：默认折叠，不占用宝贵的屏幕空间；展开后以清晰的步骤列表呈现

**为什么重要**：这个设计让用户感受到"AI 是在认真理解我的需求、为我专门找的"，而不是"系统随机给了一个结果"，直接影响用户对路线的信任度。

#### 2.3.4 路线方案展示（Route Compare）

AI 返回 2~3 条路线方案后，进入路线浏览模式：

**方案摘要卡片（可横向切换）**
- 每条路线展示：emoji + 标题、总时长、人均费用、排队时间、5 维度综合评分（品质 / 排队 / 预算 / 距离 / 偏好匹配度）
- 支持左右滑动切换方案，地图背景实时更新对应路线的标注点
- 推荐原因标签（"适合拍照""人均仅 ¥60""少排队"等）

**时间线详情（展开后）**
- 每个站点展示：时间段、站点名称、分类 tag、预计停留时长、排队等待时间（含拥挤程度图标）、人均费用、评分、封面图
- 站点之间显示交通方式和时长（步行 / 地铁 / 公交 / 出租）
- 当前正在进行的站点高亮显示（根据实际时间判断）
- 每个站点右侧有操作菜单：替换此地点、延长停留、加个休息、导航到这里、标记已完成

**快捷操作栏（Route Optimize Bar）**
- 路线下方有 4 个常用调整按钮：**换一家**（替换某个地点）/ **更省钱**（重新规划降预算）/ **少排队**（避开拥挤地点重规划）/ **亲子友好**（加入儿童适宜筛选条件）
- 还有"**跟 AI 说**"入口，直接展开输入框做自由描述修改

**突发事件面板（Smart Follow-up）**
- 在已选路线状态下，右下角或固定位置有突发事件入口
- 预设 6 种场景：餐厅排队太久 → 找替代 / 前往路上堵车了 / 有点累了想休息 / 天气变了（下雨）/ 临时多了一个人 / 想提前结束
- 点击后直接触发带上下文的重新规划请求

**路线编辑器（Route Edit Sheet）**
- 点击"编辑行程"按钮弹出底部覆盖页
- 可以多选站点后执行：上移 / 下移排序（箭头操作）、复制站点、标记替换（待 AI 处理）、删除站点
- 编辑完成后保存，路线更新并同步至地图

**行程完结页（Trip Summary Overlay）**
- 走完全部站点或手动结束后，展示本次行程总结：
  - 去了哪些地方（站点列表）
  - 总时长、人均费用
  - 5 个维度打分（路线合理性 / 餐厅满意度 / 时间安排 / 预算控制 / AI 准确度）
  - 打分后有"AI 已记住你的偏好"提示，下次规划时权重生效

#### 2.3.5 地图面板（Map）

- 全屏背景地图，使用 Leaflet + OpenStreetMap 渲染
- 路线站点以标注点形式显示，当前选中的路线高亮连线
- 用户切换路线方案时，地图实时更新对应路线的标注
- 编辑路线后，地图同步更新（通过 `onLiveStopsChange` 回调实现）
- 点击地图上的标注点，底部面板会跳转到对应站点详情
- 底部面板高度（半屏 / 全屏 / 收起）变化时，地图自动调整视野中心偏移，确保标注点不被面板遮挡

### 2.4 个人主页（Profile）— 偏好档案 & 历史记录

**这是什么**：用户的个人中心，展示偏好档案、历史行程，并提供意见反馈和关于页入口。

**具体功能点**：

#### 2.4.1 个人偏好档案展示
- 展示用户 Onboarding 时填写的所有偏好信息：
  - **常去场景**（如：🚶 街头漫游、🍜 美食探店）
  - **出行偏好**（如：少排队、步行 citywalk、人少景美）
  - **避开场景**（如：✗ 人太多、✗ 消费贵）
- 右上角有齿轮按钮，点击弹出确认弹窗后可重置偏好（重新走一遍 Onboarding 流程）

#### 2.4.2 我的行程记录
- 点击菜单项进入全屏行程记录列表页
- 历史行程按日期分组（降序），每条记录展示：
  - 行程封面图（可横滑切换多图）+ emoji 标题
  - 站点流（彩点连线展示经过的 POI）
  - 出行时间段、人均费用、评分
  - 时间进度条（按各站点时长比例着色）
- 点击历史行程可进入详情覆盖页（复用 `RouteCard` 组件，与规划页方案展示一致）
- 详情页底部有"根据此方案重新规划"按钮，点击后跳转回规划页并预填历史路线信息

#### 2.4.3 意见反馈
- 全屏覆盖的文本输入页
- 用户填写意见后点击提交，展示"感谢你的反馈！"成功状态（1.4 秒后自动关闭）

#### 2.4.4 关于「Drifto」
- 产品介绍页，含 Logo、品牌 tagline（"随漂流动，随心而行"）
- 4 个核心功能亮点介绍：智能路线规划 / 排队预测 / 边走边改 / 行程记忆
- 底部署名（美团黑客松团队「三张黑桃」）

## 三、整体技术架构简述

> 本节仅作为背景参考，非产品决策核心

- **框架**：React 19 + TypeScript，Vite 构建
- **样式**：纯 CSS 变量 + Mobile-first 媒体查询，全局 `globals.css` 单文件管理
- **状态管理**：无全局状态库，核心数据通过 `useChat` hook 集中管理，组件间通过 props 传递
- **API 交互**：SSE 流式接口（`sendChatMessageStream`）实时接收 AI 回复和路线数据
- **地图**：Leaflet + OpenStreetMap（开源，无 API Key 限制）
- **持久化**：用户偏好和行程历史存储在 `localStorage`，无需登录

## 四、当前做得好的设计决策

### 4.1 地图在背景里，不是单独页面

规划路线的过程中，地图始终作为全屏背景存在。用户不需要在"对话页"和"地图页"之间切换，规划时天然就在感受空间分布。

这个设计降低了"路线合不合理"的判断成本——用户看到路线卡片的同时，地图上的标点和连线已经让他们对空间关系有了直觉感知。

### 4.2 路线结果跟在对话后面

路线方案不是跳到新页面展示，而是直接附在最后一条 AI 回复的下方。这样设计保留了对话上下文：用户看完路线觉得不满意，直接继续说"这条太贵了换一个"，上下文不会丢失，AI 知道你说的是哪条路线。

### 4.3 AI 思考过程透明可折叠

思考过程默认折叠（手机上不占版面），但好奇的用户点开可以看到完整推理链。这是一个"存在感低、价值感高"的设计——不打扰大多数用户，同时为希望了解 AI 决策依据的用户提供满足感。

### 4.4 四个快捷操作覆盖高频调整

"换一家、更省钱、少排队、亲子友好"——这四个按钮覆盖了绝大多数用户会提出的路线调整诉求，且不需要用户自己想怎么表达，点一下就触发重新规划。这是对"自然语言门槛"的有效降级。

### 4.5 突发事件面板符合真实出行场景

真实出行中行程经常会变化。把"堵车了""排队太久""有点累了"这些场景直接做成快捷触发，承认并正面解决了"执行过程中计划赶不上变化"的问题，这是大多数路线规划工具忽视的场景。

### 4.6 偏好引导 + 首页推荐形成冷启动闭环

Onboarding 收集的偏好数据直接驱动首页"猜你喜欢"模块的内容差异化——第一次进入就能看到和自己偏好匹配的路线，而不是千篇一律的推荐，第一印象就建立了"这个 App 懂我"的感知。

## 五、当前体验短板

### 5.1 执行闭环没有打通（最关键）

**现状**：用户生成路线后，产品体验基本结束。"保存到我的行程"功能存在但体验不完整，没有清晰的"开始出发"动作，也没有出行过程中的跟随引导。

**影响**：用户拿到方案后大概率会截图保存、关闭 App，用其他工具执行（地图导航等）。这意味着产品完成了规划价值，但没有获得执行过程中的用户留存，也没有在执行结束后收回反馈。

**理想态**：用户应该能在产品内走完"规划 → 出发 → 执行 → 完成 → 反馈"的完整链路，而不是规划完就离开。

### 5.2 个性化感知不明显

**现状**：用户第一次填完偏好、第二次进来，主观体验和第一次差别不大。反馈打分功能存在，但用户感知不到"AI 记住了我的评价"。

**影响**：用户无法建立"用得越多越准"的产品认知，粘性下降，复访动力弱。

### 5.3 多方案差异化不够直观

**现状**：3 条路线需要用户逐一点开时间线才能发现区别，认知成本较高。

**影响**：用户可能因为"看不出区别"而随便选一条，或者干脆只看第一条，多方案的价值没有充分传递。

**理想态**：类似飞机票比价页面，差异点一目了然——"这条省 60 元、这条少排 45 分钟、这条更适合带娃"在标题层就能看出来。

### 5.4 天气和定位还是假数据

**现状**：规划页展示的天气（"晴 28°"）和出发位置（"北京市西城区西单"）是写死的 Mock 数据，与用户真实情况无关。

**影响**：用户如果注意到天气数据不对，会对产品的真实性产生怀疑；更重要的是，AI 规划路线时没有用到真实天气，可能给下雨天推荐户外 citywalk。

### 5.5 分享能力缺失

**现状**：产品没有任何分享功能。

**影响**：路线规划本质上是一个有社交属性的行为（约朋友出去、分享给家人），缺少分享功能意味着产品的自然传播链路被切断。

## 六、优化方向与优先级建议

### P0：打通执行闭环

**核心目标**：让用户能在产品里完成从"看到方案"到"完成行程"的全过程。

| 功能点 | 具体内容 |
|--------|---------|
| 开始出发 | 选定路线后有明确的"出发"按钮，进入执行模式，当前站点高亮 |
| 行程完成仪式 | 到达最后一站后出现完成页，展示行程小结（去了哪里、花了多少、用时多久） |
| 我的行程列表 | 待出发 / 进行中 / 已完成三个状态，历史行程可回顾 |
| 状态流转 | 行程状态在 planned → ongoing → completed 之间顺畅切换 |

### P1：让个性化可感知

**核心目标**：让用户在每次使用后都能感受到"AI 记住了我"。

| 功能点 | 具体内容 |
|--------|---------|
| 反馈后显式确认 | 打分后给一条提示："AI 已记住你更在意排队时间" |
| 复访时有记忆感 | 二次进入规划页时，AI 欢迎语中提及上次行程（"上次去了外滩，这次换个地方？"） |
| 偏好变化可见 | 在用户画像页展示权重变化趋势，让用户看到自己的"口味档案"在进化 |

### P1：优化方案差异化展示

**核心目标**：让用户在看标题时就能分辨 3 条路线的差异，不需要一一点开阅读。

| 功能点 | 具体内容 |
|--------|---------|
| 差异标签高亮 | 每条路线标题下方加一行核心差异标签，如"比其他方案省 ¥60""排队减少 40 分钟" |
| 对比视图 | 3 条路线并排时，相同地点灰显、独有地点高亮，一眼看出差异 |

### P1：接入真实天气与定位

**核心目标**：让规划依据真实环境，而不是假数据。

| 功能点 | 具体内容 |
|--------|---------|
| 真实天气 | 接入高德天气 API 或 OpenWeatherMap，替换 Mock 数据 |
| 真实定位 | GPS 已有逻辑，完善逆地理编码，在规划页准确显示当前位置 |
| 天气影响路线 | 下雨时主动提示"今天有雨，已优先推荐室内路线" |

### P2：分享能力

**核心目标**：让用户能把规划好的路线分享给同行的人，或发朋友圈。

| 功能点 | 具体内容 |
|--------|---------|
| 分享卡片 | 生成一张图：路线标题 + 3-4 个地点 + 总时长 + 人均费用，可直接分享微信 |
| 邀请同伴 | 把路线链接发给朋友，朋友可以查看并一键"用这条路线" |

### P3：长期方向探索

| 方向 | 说明 |
|------|------|
| 多人偏好合并 | 两个人或一家人偏好不同时，AI 帮找双方都能接受的折中方案 |
| 历史行为个性化 | 基于历史行程数据，AI 主动推荐"你还没去过的"或"你上次喜欢的类型" |
| 营业状态实时提醒 | 出行中某个地点临时关门或排队突然变长，主动推送提醒并给备选 |

## 七、核心指标建议

以下是衡量产品是否真正解决了用户问题的关键数据指标：

| 指标 | 含义 | 目标参考 |
|------|------|---------|
| 路线生成成功率 | 用户发出请求后能得到路线的比例 | ≥ 90% |
| 首次出方案率 | 第一轮对话后直接出路线（不需要追问）的比例 | ≥ 80% |
| 路线保存率 | 生成路线后保存到"我的行程"的比例 | ≥ 40% |
| 行程启动率 | 保存的行程中实际点击"开始出发"的比例 | ≥ 30% |
| 行程完成率 | 启动后走到"完成行程"的比例 | ≥ 50% |
| 反馈提交率 | 完成行程后提交评分的比例 | ≥ 25% |
| 7 日复访率 | 首次使用后 7 天内再次使用的比例 | ≥ 30% |

## 八、总结

### 已经做对的事

- 对话 + 地图的产品形态选择是对的，符合"出行工具"的心智
- 思考过程透明化是差异化亮点，让用户感知到"这是为我定制的"
- 突发事件重规划是少见但真实有价值的功能
- 快捷操作降低了"不知道怎么说"的门槛，提升了调整体验
- Onboarding 与首页"猜你喜欢"形成了冷启动的完整数据闭环，用户第一次进来就能看到个性化内容

### 还没做完的事

- **执行闭环**是当前最大的缺口，规划完成之后产品就"断了"
- **个性化感知**还是概念，用户体感上还没有"越用越懂我"
- **天气和定位**用的假数据，影响规划的真实性和可信度
- **分享能力**缺失，切断了最自然的社交传播路径

### 一句话结论

> 这个产品在"帮用户想清楚去哪"上已经做得相当不错；接下来最重要的一步，是**帮用户真正出发**，而不是规划完就结束。

## 九、版本演化历程：从复杂到简单

### 9.1 第一版：功能齐全但链路繁琐

项目初期的前端设计，思路是"把所有功能都做进去"。在当时的方案里：

- **首页是一个内容推荐页**，类似小红书或大众点评，展示精选路线卡片、热门地点、分类 Tab 等内容模块，用户要浏览完这些内容，才能找到入口进入规划
- **进入对话的方式是底部 Tab 栏的"+"按钮**，类似微信的"发现"或大众点评的新建日程，这个交互路径不够直接——用户想规划出行，却需要先在内容页停留，再找到底部的加号，才能到达真正的核心功能
- **Tab 栏本身**包含首页 / 规划 / 我的等多个 Tab，整体产品框架更像是传统 App 的信息架构，而不是以对话为核心的 AI 工具

这版的问题在于：结构越复杂，用户从"打开 App"到"AI 开始帮我规划"之间的步骤就越多。每多一步，流失和困惑就增加一分。

### 9.2 关键简化：移除 Tab 栏，重塑首页定位

经过团队对齐，识别出核心问题：**这个产品的价值主张是"一句话，AI 出行程"，但流程设计和这个价值主张是矛盾的**。

于是做了几个关键决策：

**第一，砍掉 Tab 栏**。Tab 栏适合有并列功能模块的工具，但 Drifto 的核心体验是"对话 + 规划"，Tab 栏的存在反而在分散用户注意力，让产品看起来像内容平台，而不是 AI 助手。移除后，整个产品只有两种状态：还没开始规划 / 正在规划。

**第二，首页重新定位为"发起规划的起点"**，而不是"内容浏览页"。精选路线推荐（"猜你喜欢"）从首页的主角降级为辅助模块，核心位置让给输入框。用户打开 App，第一眼就看到的是"你可以说什么"，而不是"你应该看什么"。

**第三，弹幕推荐问句替代了内容卡片列表**。原来的精选路线卡片需要用户一条一条点开看，成本较高；改为轮播的推荐问句后，用户只需要点一下，就能把一个具体的出行场景想法填入输入框，门槛降低了一个数量级。

**第四，Onboarding 前置到首次进入**。用户画像的收集从"某个设置页里的功能"变成了"进入产品的第一件事"，这让偏好数据的收集时机更自然，也让"AI 在规划之前就了解我"成为可能。

### 9.3 规划页：从多页面跳转到单页叠加

早期设计中，对话、路线方案、地图是三个相对独立的视图，用户需要在它们之间来回切换。这在桌面端还好，但在手机上切换页面的成本很高——每次跳转都会中断上下文感知，用户容易在"我在哪""我刚才在看什么"上产生困惑。

最终版本把三者合并在一个页面里：
- **地图**作为全屏背景，始终可见，不再是独立页面
- **底部面板**是可拖拽的浮层（BottomSheet），承载对话、方案选择、路线详情等所有内容，通过上下拖动控制"看地图的比例"和"看内容的比例"
- **路线方案直接附在 AI 回复之后**，不跳转新页面，上下文完整保留

这一结构降低了用户在"规划"和"感知空间"之间的切换成本，让整个体验流动性更强。

### 9.4 迭代节奏中的关键修复

版本演化不只是功能的增减，还有大量"做了才发现不对"的细节修复，典型的几个：

| 问题 | 原因 | 修复方式 |
|------|------|---------|
| 删节点后地图不响应 | 地图数据依赖 `response.routes` 引用，节点删除未触发引用变化 | 引入独立 `mapStops` state，与 routes 数据解耦 |
| 多轮对话上下文丢失 | AI 每轮都重新理解意图，未继承上轮约束 | 引入 `TripState` + `QueryDelta` 机制，多轮只传变化部分 |
| 思考过程展示技术感太强 | 直接暴露"召回 46 个候选""置信度 87%"等内部字段 | 统一转化为自然语言叙述，隐藏工程细节 |
| 路线方案感知不到差异 | 三条路线标题相近，内容需点开才能分辨 | 后端新增推荐理由 tag，前端在标题层展示差异标签 |
| 追问体验生硬 | AI 直接反问，没有过渡引导语 | 追问前先插入"我想了解这些信息来帮你规划"的前置消息 |
| 行程完结评价无法触发 | 删节点后节点索引变化导致条件判断失效 | 修改触发条件为"评价卡未展示且未结束"，而非依赖索引 |

## 十、开发经验总结

### 10.1 先跑通链路，再追求体验

前端开发的顺序应该是：**链路跑通 → 能用（稳定不崩） → 可用（符合直觉） → 好用（体验细节）**。

这个顺序容易被忽视。很多时候，前期会忍不住花时间在动画效果、UI 细节、边界状态的视觉处理上，但如果核心链路还不通，这些工作都是在做浮在空中的装饰。

在本项目中，最优先保障的是：用户输入 → 后端收到请求 → 返回路线数据 → 前端正确渲染路线卡。这条链路走通之后，再一层一层叠加体验细节（思考过程、骨架屏、地图联动、快捷操作……）。

### 10.2 频繁与团队对齐，比自己猜测更有效

本项目是多角色协作（Agent 后端 / 路线策略 / 前端 UI），很多前端的设计决策需要对齐后端的数据结构和返回格式。

实践下来，最有效的方式是：
- **不等接口"完美"再对接**，用 Mock 数据先把前端走完，再换真实接口
- **每次接口字段变动，写版本日志**（项目里的 `version_log.md` 就是这个作用），而不是靠口头沟通或改完悄悄上线
- **前端与后端约定字段时，以"前端能不能直接用"为标准**，而不是"后端方便怎么返回"——这两者有时候不一致，需要明确谁来做转换

### 10.3 产品简化是有取舍成本的，需要团队共识

砍掉 Tab 栏、重塑首页这类简化决策，看起来是"少做了一些东西"，但实际上需要整个团队承认一件事：我们对自己产品的定位想清楚了，它是 AI 对话工具，不是内容平台。

这个认知对齐需要时间，也需要实际做出来对比。当第一版的复杂结构和简化后的版本都能看到的时候，差异是直观的，讨论成本低了很多。**让代码说话，比讲道理更有说服力。**

### 10.4 移动端 UI 的特殊性需要从一开始就考虑

很多 Web 端看起来合理的设计，到了手机上会暴露问题：

- **底部 Tab 栏的触达成本**：手指需要从屏幕中上部移动到最底部，对单手操作不友好
- **多页面跳转的上下文断裂**：手机屏幕小，跳转页面会让用户失去"我刚才在哪"的感知
- **输入法弹起对布局的破坏**：输入框如果不处理好 `safe-area-inset-bottom`，会被虚拟键盘遮住
- **触摸滑动的方向冲突**：横向滑动卡片和纵向滚动页面容易相互干扰，需要明确方向锁定逻辑（项目中在图片横滑和卡片列表滚动之间专门处理了这个问题）

这些问题如果在后期才发现，修改成本远高于从设计初期就以移动端为主。

### 10.5 调试工具和日志要作为功能一起做

项目中有一个 LLM 健康检查面板（Debug Panel），可以直接看到请求/响应历史、Agent 的实时推理过程。这不只是"给开发用的工具"，在团队联调阶段，它极大地降低了沟通成本——当 A 同学说"这条请求 AI 没有理解对"的时候，前端可以直接展示 trace 数据，不需要对方重新描述问题。

调试能力是团队协作效率的乘数，值得在开发早期就投入。
