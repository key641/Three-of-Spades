# 意图理解与需求澄清方案

## 目标

本方案用于规范用户 query 进入系统后的第一层判断：先识别用户本轮意图属于哪一类，再决定是否需要澄清、生成路线、重规划或回答路线问题。

核心目标不是“尽可能多问问题”，而是“只在无法生成可执行路线时才追问”。对于路线生成必须的信息，如果系统没有获得，需要澄清；对于非必要信息，可以使用默认值、用户画像或当前会话上下文补齐，避免因为问题太多造成用户疲劳。

## 核心原则

### 1. 先判断意图类型，再决定是否澄清

系统收到用户 query 后，不应直接进入路线生成，也不应直接追问。第一步应判断本轮 query 属于哪种类型：

- 新路线规划
- 全量重规划
- 局部重规划
- 路线细节追问
- 需求澄清回复
- 普通闲聊或非路线问题

只有当本轮意图需要生成或调整路线，并且缺少关键字段时，才进入澄清。

### 2. 优先澄清路线生成必须的信息

必须信息指“缺失后无法生成可信路线，或者生成结果大概率不可执行”的字段。比如城市完全缺失时，系统无法知道去哪里召回 POI；用户只说“帮我安排一下”时，也无法判断是吃饭、游玩、通勤还是亲子出行。

非必须信息不应打断用户。比如人数、预算、出发时间、偏好等字段可以有默认值，也可以从用户画像和历史上下文中推断。

除了路线生成必须字段外，还有一类澄清来自“意图分类不清”。如果系统无法确认用户到底是在新规划、全量重规划、局部重规划、路线追问之间选择哪条链路，也应触发澄清。此时追问的目的不是补字段，而是确认用户想让系统做什么。

### 3. 问题要少，优先问最关键的问题

即使缺多个字段，也不要一次抛出长问卷。系统应按优先级优先询问当前最影响路线生成的问题。默认情况下只问一个关键问题；如果确实存在两个互相依赖、缺一不可的信息，也可以合并成一个轻量问题，但整体要保持问题少、负担低。

例如用户说：

> 帮我安排一个周末路线

更好的追问是：

> 你想在哪个城市或区域玩？我确认地点后就能先给你出一版路线。

不建议一次问：

> 你在哪个城市、几个人、几点出发、预算多少、喜欢吃什么、想玩多久？

### 4. 可默认的信息先默认，并在结果中轻提示

如果字段缺失但可以默认，系统应直接生成路线，并在回复中轻量说明默认假设。

例如：

> 我先按 1 人、上午 9 点出发、人均 300 元左右规划。你补充出发点后，我可以再帮你重算交通时间。

### 5. 利用已有上下文，避免重复确认

如果 session 中已经有城市、时间、预算、路线或用户画像，本轮 query 没有明确覆盖它们时，应优先继承上下文，而不是重复问用户。

例如上一轮已经生成“上海一日游”，用户本轮说“少排队一点”，系统应识别为全量重规划，并继承上海、一日游、预算等约束。

### 6. 低置信度时优先确认，避免错误执行

如果系统判断用户意图的置信度很低，或者 query 同时可能属于多个类型，应先做轻量确认，而不是贸然规划。交互上的基本原则是：如果不清晰，不能替用户瞎做决定。

低置信度追问不是为了收集更多偏好，而是为了确认“该走哪条处理链路”。例如系统无法判断用户是想全量重规划，还是只想局部替换当前路线中的某个点，就应该先确认。

例如：

> 你是想重新生成一条更省钱的路线，还是只想把当前路线里的某一家店换掉？

如果系统能在几个意图之间判断出明确倾向，但仍有少量不确定，可以先执行高置信度路径，并在回复里说明自己的理解。例如：

> 我理解你是想把当前路线整体改得更省钱一点，我会保留城市和时间，重新生成一组省钱方案。

## 意图类型划分

| 意图类型 | 判断标准 | 示例 | 是否需要澄清 |
| --- | --- | --- | --- |
| 新路线规划 | 用户从零提出出行或游玩目标 | 我想去上海一日游；周末带娃玩一天 | 缺关键字段或目标过泛时澄清 |
| 全量重规划 | 用户改变整体偏好、预算、节奏或路线目标 | 更省钱一点；少排队一点；亲子友好一点 | 通常不澄清，继承原硬约束后重算 |
| 局部重规划 | 用户针对已有路线中的某一部分做调整 | 换一家；这家排队太久；下雨了怎么办 | 如果无法定位影响点，才澄清 |
| 路线细节追问 | 用户询问已有路线的原因、交通、费用或注意事项 | 为什么推荐这家？第二站怎么去？ | 不澄清，直接基于当前路线回答 |
| 需求澄清回复 | 用户回答上一轮系统追问 | 在上海；两个人；预算 300 | 不重新分类为新需求，补齐缺失字段 |
| 普通闲聊或非路线问题 | 与路线规划无关 | 你是谁？今天星期几？ | 不进入路线规划链路 |
| 意图不确定 | 系统无法在多个意图之间稳定判断 | 换个便宜点的；这个不太行 | 先确认用户想全量重规划、局部替换还是只是追问 |

## 字段澄清优先级

### 必须澄清字段

这些字段缺失时，通常无法生成稳定路线。

| 字段 | 为什么必须 | 可接受替代 |
| --- | --- | --- |
| 城市或明确区域 | 决定 POI 召回范围和地图路线 | 如果上下文已有城市，可继承 |
| 出行目标类型 | 决定是游玩、吃饭、citywalk、亲子、夜游等 | 如果用户话术已隐含目标，可由 LLM 解析 |
| 是否引用当前路线 | 决定是新规划、全量重规划还是局部重规划 | 如果有“换一家、这家、第二站”等指代，需要当前路线上下文 |

### 条件性澄清字段

这些字段不是每次都问，只有在影响执行或用户表达冲突时才问。

| 字段 | 什么时候澄清 | 默认策略 |
| --- | --- | --- |
| 出发点 | 用户要求精确交通、地图路线、通勤时间时 | 默认城市中心或热门起点 |
| 游玩时长 | 用户没有说半天/一天/晚上，且无法从上下文继承时 | 默认 8 小时 |
| 出发时间 | 用户关心营业时间、夜游、餐饮饭点时 | 默认 09:00 |
| 人数和同行人 | 涉及亲子、老人、多人预算时 | 默认 1 人 |
| 预算 | 用户强调省钱、高端、吃好时 | 默认中等预算 |
| 交通方式 | 用户要求少走路、开车、地铁优先时 | 默认步行 + 地铁 + 打车综合 |

### 不需要澄清字段

这些字段可以由系统默认、用户画像或路线评分算法处理。

| 字段 | 处理方式 |
| --- | --- |
| 具体餐厅口味 | 先按用户画像和 POI 标签推荐 |
| 是否网红打卡 | 作为偏好权重，不阻塞路线生成 |
| 是否少排队 | 作为路线目标或评分权重，不阻塞路线生成 |
| 是否室内 | 作为偏好或天气场景，不阻塞路线生成 |
| 预算精确数值 | 没有明确预算时使用默认预算档 |
| 每个 POI 停留时间 | 由 POI 数据的平均游玩时长估算 |

## 澄清决策流程

```text
收到用户 query
  ↓
识别本轮意图类型
  ↓
检查意图分类置信度
  ↓
如果置信度过低，且可能进入不同处理链路：先确认用户意图
  ↓
判断是否需要路线生成或路线调整
  ↓
如果只是路线追问或闲聊：直接回答
  ↓
如果需要生成路线：
  ↓
合并用户 query、session 上下文、用户画像、默认值
  ↓
检查是否缺少必须字段
  ↓
缺少必须字段：优先追问最关键问题，保持问题少
  ↓
不缺必须字段：进入 POI 召回、路线生成、评分与解释
```

说明：这里的“只追问 1 个最关键问题”是默认交互策略，不是绝对限制。实际产品中应以“问题少、用户负担低”为准；如果一个轻量问题可以同时确认两个强相关信息，可以合并询问。

## 默认值策略

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| 人数 | 1 人 | 用户没有说明时默认个人出行 |
| 出发时间 | 09:00 | 适合一日游和半日游起点 |
| 游玩时长 | 8 小时 | 用户说“一日游”时使用；半日游可用 4 小时 |
| 人均预算 | 300 元 | demo 阶段默认中等预算 |
| 出发点 | 城市中心或热门商圈 | 生成路线时可先用，用户补充后重算 |
| 交通方式 | 步行、地铁、打车综合 | 由距离和 POI 交通推荐自动选择 |
| 路线目标 | 综合平衡 | 没有明确偏好时输出综合、少排队、省钱等多方案 |

## 澄清话术规范

### 好的澄清话术

好的澄清应该短、明确、只问一个问题，并说明为什么要问。

示例：

> 想在哪个城市或区域玩？我确认地点后就能先给你出一版路线。

> 你是想把当前路线里的这家店换掉，还是想整条路线都更省钱一点？

> 这次是半天还是一整天？这个会影响我安排几个 POI。

### 不好的澄清话术

避免像问卷一样连续抛问题。

不建议：

> 请告诉我城市、人数、预算、出发时间、出发点、交通方式、饮食偏好、是否亲子、是否室内。

也不建议：

> 信息不足，请补充更多信息。

## 与现有模块的关系

### MessageRouter

负责第一层意图路由，输出：

- `intent_type`
- `planning_mode`
- `inherit_previous`
- `references_previous_route`
- `confidence`

它决定本轮 query 是新规划、全量重规划、局部重规划、路线追问还是普通聊天。

### IntentParser

负责从自然语言中抽取结构化字段：

- 城市
- 人数
- 出发时间
- 游玩时长
- 预算
- 偏好
- 避开项
- 场景

### ClarificationPolicy

建议新增独立策略层，专门判断是否需要澄清。它不负责解析意图，也不负责生成路线，只回答三个问题：

- 当前意图是否需要澄清？
- 如果需要，缺哪个关键字段？
- 应该问用户哪一个问题？

它需要同时处理两类澄清：

- 字段缺失澄清：缺少城市、目标类型等路线生成必须信息。
- 意图确认澄清：意图分类置信度太低，无法稳定选择新规划、全量重规划、局部重规划或路线追问。

建议输出结构：

```json
{
  "need_clarification": true,
  "clarification_type": "missing_required_field",
  "missing_field": "city",
  "priority": "required",
  "question": "想在哪个城市或区域玩？我确认地点后就能先给你出一版路线。",
  "can_continue_with_defaults": false,
  "candidate_intents": []
}
```

如果是意图确认澄清，可以输出：

```json
{
  "need_clarification": true,
  "clarification_type": "intent_disambiguation",
  "missing_field": null,
  "priority": "routing",
  "question": "你是想重新生成一条更省钱的路线，还是只想把当前路线里的某一家店换掉？",
  "can_continue_with_defaults": false,
  "candidate_intents": ["full_replan", "partial_replan"]
}
```

### Orchestrator

负责串联完整流程：

1. 调用 MessageRouter 判断意图类型。
2. 调用 IntentParser 解析结构化字段。
3. 合并 session 上下文和用户画像。
4. 调用 ClarificationPolicy 判断是否需要追问。
5. 不需要澄清时，进入 POI 召回和路线生成。

## Demo 阶段建议实现范围

第一阶段只做最小可用澄清，不做复杂问卷。

### 必做

- 城市缺失时澄清。
- 新规划目标过泛时澄清。
- 意图分类置信度过低，且可能进入不同处理链路时澄清。
- 局部重规划无法定位当前路线或目标 POI 时澄清。
- 默认只问一个最关键问题，必要时允许合并少量强相关问题。
- 非必要字段使用默认值，并在回复中轻提示。

### 暂不做

- 不做多页问卷。
- 不做复杂偏好量表。
- 不强制询问预算、人数、出发点。
- 不因为画像字段缺失而阻塞路线生成。

## 示例场景

### 场景 1：必须澄清城市

用户：

> 周末帮我安排一日游

系统：

> 想在哪个城市或区域玩？我确认地点后就能先给你出一版路线。

原因：城市是 POI 召回和地图路线的必要范围。

### 场景 2：不澄清预算和出发点

用户：

> 上海一日游，想少排队

系统行为：

- 不追问预算。
- 不追问出发点。
- 默认 1 人、09:00 出发、8 小时、人均 300 元。
- 生成少排队倾向路线。
- 回复中提示可补充出发点后重算交通。

### 场景 3：全量重规划不澄清

用户：

> 更省钱一点

系统行为：

- 识别为全量重规划。
- 继承上一轮城市、人数、时间、路线场景。
- 增加省钱偏好。
- 重新召回 POI 并生成新方案。

### 场景 4：局部重规划需要定位

用户：

> 换一家

如果当前路线只有一个餐厅，系统直接替换。

如果当前路线有多个餐饮点，系统追问：

> 你想换掉哪一站？可以说“午餐那家”或“第二站”。

### 场景 5：路线追问不澄清

用户：

> 为什么推荐第二站？

系统行为：

- 识别为路线细节追问。
- 不重新规划。
- 基于当前路线、POI 标签、评分理由回答。

## 成功标准

- 用户输入明确城市和目标时，系统能直接生成路线，不被多余问题打断。
- 用户输入过泛时，系统优先追问最关键问题，整体问题少、负担低。
- 非必要字段缺失时，系统使用默认值继续规划。
- 多轮场景中，系统能继承上下文，避免重复问城市、人数、预算等信息。
- “换一家”和“更省钱一点”能走不同链路：前者局部重规划，后者全量重规划。

## 后续迭代方向

- 增加澄清问题的置信度阈值。
- 对不同场景设置不同必填字段，例如亲子、夜游、餐饮、通勤。
- 将澄清问题作为前端可点击选项展示，降低输入成本。
- 根据用户历史行为调整澄清策略，对熟悉用户少问，对新用户轻问。
- 增加“先出一版”的按钮，让用户可以跳过非必要澄清。
